# Teaching workflow control

## Resolve and plan

Identify the course/offering, requested deliverables, canonical sources and destinations. Read the nearest applicable repository instructions, adopted syllabus and policies relevant to the change. Inspect current working/index state before editing. Reuse an existing coordinator's plan, confirmed inputs and review evidence. A bounded subagent owns only its assigned output; the coordinator owns integration and release.

For a one-field correction, a one-line plan suffices. For multiple deliverables, state the ordered outputs, dependencies, checks and publication boundary. Execute an already authorized plan; do not create extra approval gates. Ask only for missing consequential choices, genuine conflicts or authority not supplied by the request. An applicable explicit plan-confirmation requirement still applies. Continue independent supported work while blocked portions wait.

Current adopted policies and accepted decisions govern course choices; old webpages are baselines. Official institutional sources govern current scheduling/requirements. Surface conflicts rather than choosing by modification time or treating a preview as canonical. Never silently amend adopted grading or assessment policy. Research dates for the requested offering, not automatically the current term.

## Control the handoffs

Use one sequence: resolve → draft/edit → validate/review → ready → authorized publication → verify. A failed check returns only affected work to revision. Missing sources, consequential uncertainty or failed required review prevent the affected artifact from being called ready. Review actual final content, not a superseded draft. Preserve supported progress and state the exact blocker.

Publication authority comes from the current request and selected leaf's disclosed behavior. Syllabus and assessment generation are private by default. A webpage update or default course-note workflow includes its scoped commit/push unless the user restricts it. Confirm unresolved policy changes before adoption, and private assessments/keys before release. Do not broaden a routine request into course initialization or repository-wide reconciliation.

At the publication handoff, identify the exact approved files, destination and release scope. Let `update-course-webpage` own the one commit/push for a shared website change; never call it twice through both wrapper and leaf. Preserve unrelated working and staged changes and inspect all outgoing commits.

Finish with artifact/page paths, what changed, validation/review evidence, publication status and unresolved decisions. Distinguish a draft, a local commit, a successful push and a deployed page. Unchanged inputs should reuse existing outputs, approvals and links without cosmetic rewrites or duplicate records.
